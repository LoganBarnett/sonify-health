#+title:     Contributing to sonify-health
#+language:  en

Guidelines for contributing to sonify-health.

* Document conventions

- *Root-level UPPER_CASE names* are reserved for the standard set: =README=,
  =CONTRIBUTING=, =LICENSE=.  All other documentation lives in =docs/= with
  lower-kebab-case file names (e.g. =docs/systemd.org=).
- Every document must be reachable — directly or indirectly — from =README.org=.
- Use org-mode for all new documents.

* Development environment

Enter the Nix dev shell before running any commands:

#+begin_src sh :results none :exports code
nix develop
#+end_src

Or, if you use direnv:

#+begin_src sh :results none :exports code
direnv allow
#+end_src

* Code style

** Semantic error handling

This project uses *semantic error types* with ~thiserror~ rather than generic
error wrapping with ~anyhow~.  Every error variant must include sufficient
context to diagnose the problem without access to the source code or the running
environment.

See ~crates/cli/src/config.rs~ for examples of well-structured error types.

** Comments

Comments must be complete sentences, wrapped at 80 columns, with standard
punctuation.  Only comment non-obvious intent, invariants, tradeoffs, or
historical constraints; do not restate control flow.

** Initialisms

Use Pascal initialisms (~Url~) instead of preserved initialisms (~URL~) when
authoring new identifiers in camel case.

** Control flow: prefer expressions over early returns

Rust is expression-oriented — ~if~/~else~, ~match~, and blocks all yield values.
Prefer that shape: produce a value with an ~if/else if/else~ chain, a ~match~,
or a combinator (~map~, ~unwrap_or_else~, ~map_or_else~) rather than scattering
early ~return~ statements that each yield a different value.  The indentation of
an expression tree /shows/ how much the code branches; a stack of guard-clause
returns is flat in indentation only, and hides that branching from the reader.

The one early return to keep is the uniform one: ~?~, and a bare guard clause
with no ~else~.  Every ~?~ means the same thing — propagate this error unchanged
— so it converges on a single exit rather than spidering out to many distinct
return values.  That uniformity is what makes it readable where a hand-written
~return Err(...)~ in the middle of a function is not.

Bad — an early return that yields a distinct value, followed by an ~if/else~
that is really an ~else if~:

#+begin_src rust :results none :exports code
if output.status.success() {
    return Ok(Some(parse(&output)?));
}
if ref_resolves(git_ref)? {
    Ok(None)
} else {
    Err(missing_ref(git_ref))
}
#+end_src

Good — one expression whose branches sit at the same level, so the three
outcomes read as one decision:

#+begin_src rust :results none :exports code
if output.status.success() {
    Ok(Some(parse(&output)?))
} else if ref_resolves(git_ref)? {
    Ok(None)
} else {
    Err(missing_ref(git_ref))
}
#+end_src

This is the /least-powerful-construct/ rule applied to control flow; see
~llms.org~ "Rule of least power" for the principle and the combinator clippy
lints that enforce its mechanical part.  Those lints catch manual combinator
reimplementations, not early returns — whether a guard clause should collapse
into an expression is a judgment the author makes, not something a lint decides.

* Error handling

This project uses *semantic error types* with ~thiserror~ rather than generic
error wrapping with ~anyhow~.

** Why not ~anyhow~?

While ~anyhow~ is convenient, it encourages lazy error handling that loses
important context.  When an error occurs in production you often only have logs
to work with.  A bare "No such file or directory" message with no indication of
/which/ file or /what/ operation failed is not actionable.

** Core principle: always add context

All errors must include sufficient context to diagnose the problem without
access to the source code or the running environment.

Use semantic error types that explain what went wrong and why:

#+begin_src rust :results none :exports code
use thiserror::Error;

#[derive(Debug, Error)]
pub enum ConfigError {
    #[error("Failed to read configuration file at {path:?} \
             during startup: {source}")]
    FileRead {
        path: PathBuf,
        #[source]
        source: std::io::Error,
    },

    #[error("Failed to parse configuration file at {path:?}: \
             {source}")]
    Parse {
        path: PathBuf,
        #[source]
        source: toml::de::Error,
    },

    #[error("Configuration validation failed: {0}")]
    Validation(String),
}
#+end_src

** Guidelines

- Every error variant should explain what operation failed and include relevant
  data (file paths, addresses, etc.).
- Use ~#[source]~ to preserve the full error chain.
- For file operations, include the path and (where useful) the current working
  directory.
- Never log sensitive data (passwords, tokens, connection strings with
  credentials).
- ~anyhow~ is acceptable only in throwaway prototypes.  Once you know what
  errors can occur, convert to semantic types.

** Error type hierarchy

Structure error types in layers:

1. *Low-level* (libraries/modules) — specific to that component.
2. *Mid-level* (business logic) — domain-specific.
3. *Top-level* (main.rs) — application lifecycle.

Each layer adds context about what the application was trying to do.

* CSS

** Flat selectors only

Each selector targets exactly one element type.  No nesting, no combinators, no
~>~ or ~+~ chains.  If an element needs unique styling, use a class or ID — not
a compound selector.

Good:

#+begin_src css :results none :exports code
nav {
  margin-bottom: 1rem;
}
#+end_src

Bad — nested combinator creates implicit coupling between elements:

#+begin_src css :results none :exports code
.container > nav {
  margin-bottom: 1rem;
}
#+end_src

** CSS variables for shared values

Use CSS custom properties (variables) defined on ~:root~ for any value shared
between selectors.  Never hard-code colours, spacing scales, or font stacks
directly in a selector.

Good:

#+begin_src css :results none :exports code
:root {
  --color-text: #111111;
}

p {
  color: var(--color-text);
}

h1 {
  color: var(--color-text);
}
#+end_src

Bad — duplicated literal makes updates error-prone:

#+begin_src css :results none :exports code
p {
  color: #111111;
}

h1 {
  color: #111111;
}
#+end_src

** Light and dark mode

Provide light-mode values in ~:root~ and override them inside ~@media
(prefers-color-scheme: dark)~.  Never create separate selectors per colour
scheme — the variables handle the switch.

The at-rules in the examples below are prefixed with an empty CSS comment
(~/**/~).  That is an artifact of this file, not of the style: ~llms.org~
imports ~CONTRIBUTING.org~ into the assistant's context, and the importer reads
a line that begins with ~@~ as an import path — even inside a source block.  The
comment puts a non-~@~ character at the start of the line so a stray ~media~
file cannot get pulled into every session.  Write the at-rule bare in real
stylesheets.

Good:

#+begin_src css :results none :exports code
:root {
  --color-bg: #ffffff;
}

/**/@media (prefers-color-scheme: dark) {
  :root {
    --color-bg: #111111;
  }
}

body {
  background: var(--color-bg);
}
#+end_src

Bad — duplicated selector with hard-coded colours:

#+begin_src css :results none :exports code
body {
  background: #ffffff;
}

/**/@media (prefers-color-scheme: dark) {
  body {
    background: #111111;
  }
}
#+end_src

** No inline styles in Elm

All presentation belongs in the stylesheet.  Elm views must not use ~style~
attributes.  Use semantic HTML elements (~main_~, ~nav~, ~header~, ~section~) so
that element selectors in CSS are sufficient and classes are rarely needed.

Good:

#+begin_src elm :results none :exports code
view model =
    main_ []
        [ nav [] [ ... ]
        , viewPage model
        ]
#+end_src

Bad — inline styles bypass the stylesheet and cannot respond to dark mode, media
queries, or future design changes:

#+begin_src elm :results none :exports code
view model =
    div [ style "padding" "2rem" ]
        [ nav [ style "margin-bottom" "1rem" ] [ ... ]
        , viewPage model
        ]
#+end_src

* Systemd secrets

The NixOS module uses systemd's ~LoadCredential~ to pass secret files to the
service without granting the service user direct read access.  See
=docs/systemd.org= for the full pattern.

* Code-review Stop hook

Claude Code sessions in this project run a deterministic code-review gate: the
Stop hook at =.claude/hooks/review-stop.sh= blocks a turn from ending while
un-reviewed changes sit in the working tree, first until the workspace passes
the clippy gate CI enforces (for Rust changes), then until the
=template-compliance= subagent has run and reported =COMPLIANCE: PASS=.  Plan
mode, being read-only, never triggers it.

The gate itself is the =rust-template-review-stop= binary; the hook script only
execs it.  The binary comes from the template repository's flake — the
=foundation= input — through this project's dev shell, so inside =nix develop=
(or with direnv) it is already on =PATH=, and a fix to the gate reaches this
project on a =foundation= bump rather than a file sync.  Its behaviour and tests
live in that repository's =review-stop= crate; do not fork the logic into the
hook script — a hook that stops delegating to the binary is flagged by
compliance.

*Running an LLM coding agent outside the Nix dev shell* — Claude Code today, and
any other agent that honours the same hook — requires you to put
=rust-template-review-stop= on =PATH= yourself.  The hook does not fetch or
build it, and how it gets there is not something this project can dictate.  Two
routes that work: the template repository's GitHub releases carry a binary for
every mainstream target, and cargo can build the same version the flake pins:

#+begin_src sh :results none :exports code
cargo install --git https://github.com/LoganBarnett/rust-template.git \
  --tag v<version> rust-template-review-stop
#+end_src

Whichever route, keep it at the same version as the =foundation= input so the
gate and the reviewer agent stay in step.  When the binary is missing, the exec
fails and Claude Code reports the hook error on every Stop rather than silently
skipping the gate — the loud failure is deliberate.

* Logging levels

Use appropriate log levels for different severity:

- ~error!()~ — errors that prevent normal operation.
- ~warn!()~ — recoverable issues or degraded functionality.
- ~info!()~ — important state changes.
- ~debug!()~ — detailed diagnostic information.
- ~trace!()~ — very verbose debugging.

Never log sensitive data (passwords, tokens, secrets).

* Formatting

Run ~cargo fmt~ before committing.  The pre-commit hook enforces this
automatically, so commits made outside the Nix shell may be rejected if
~rustfmt~ is not on ~PATH~.

* Testing

Run the full test suite after every change:

#+begin_src sh :results none :exports code
nix develop --command cargo test --workspace
#+end_src

Tests must exit with a proper error code.

* UI philosophy: no modals

Do not use modals anywhere in the UI.  Replace every modal with an inline
expansion that keeps surrounding context visible.

** Why

Modals block the UI — which may contain information relevant to the decision at
hand — and they are an accessibility nightmare (backdrop divs, tab-index
trapping, z-index layering).  As an interface matures, the probability of
needing a modal inside a modal trends to 1.  Powerful UIs do not use modals.

** Patterns

- *Export / large output*: clicking the trigger button slides the surrounding
  content down and reveals the output inline, in the normal document flow.
- *Destructive confirmations*: replace the triggering button in-place with a
  "Confirm delete?  Yes / No" prompt.  When the user decides (or clicks
  elsewhere), restore the original button.
- *Progressive disclosure*: expand a section in-place rather than overlaying.

Every piece of revealed UI must live in the normal document flow.  No backdrop
divs, no tab-index trapping, no z-index layering.

* UI philosophy: every label earns a help entry

The dashboard carries a lot of specialised vocabulary — metric tiers, patches,
notes, playback modes, transitions — and a contributor (or a returning user)
cannot realistically remember what each one means.  The bottom-of-page Help
panel exists to answer that question in place, without navigating away.

** Definition of Done for UI changes

Any new or renamed UI label, section header, or control caption is not
considered done until it has a corresponding entry in ~frontend/src/Help.elm~.
That means:

1. Pick a stable kebab-case ~Key~ (e.g. ~"metric-tiers"~, ~"patch-detune"~).
   Prefer names that survive cosmetic renames.
2. Add a case to ~Help.lookup~ returning one or two sentences.  Keep it short —
   the panel is small by design.  Longer explanations belong in ~docs/~.
3. Render the label with ~class "help-label"~ on a ~button~ element (not a plain
   ~span~ or ~label~) so keyboard and screen-reader users get proper semantics
   for free.  Wire its ~onClick~ to ~HelpClicked "your-key"~.

If a label has no explanation beyond "it does what it says," that is still a
one-sentence help entry — write it anyway, because what seems obvious to the
author is rarely obvious to a newcomer.

* Commit workflow

1. Make your changes on a feature branch.
2. Ensure ~cargo fmt~ and ~cargo clippy --workspace~ produce no warnings.
3. Run ~cargo test --workspace~ and confirm all tests pass.
4. Open a pull request against ~main~.

* Release binaries

A release builds your binary crates for the mainstream targets and attaches them
to the GitHub release.  The macOS binaries are *cross-compiled on Linux* (via
zig) rather than on a macOS runner, so a release never waits on scarce macOS CI
capacity.  This is automatic — ~mkDarwinCrossPackages~ is already wired into
~flake.nix~ and needs no configuration.

Each Linux target ships two variants, both automatic and both runnable off the
Nix store.  The ~-musl~ variant is fully static with no runtime library
dependency — the right choice for a self-contained tool.  The ~-gnu~ variant is
a portable dynamic build (~mkGnuPortablePackages~, via zig against a glibc 2.17
floor) that links the host's shared libraries at runtime; choose it for a tool
that must use a host library with a runtime plugin or ~dlopen~ ecosystem, which
static linking cannot absorb.  This project is exactly that case: its audio
stack links ~libasound~, which loads the host's PulseAudio/PipeWire PCM plugins
via ~dlopen~, so the ~-gnu~ build plays on a normal desktop while ~-musl~ suits
a headless host that owns the sound device.  A library added to a crate's
~buildInputs~ is picked up by both variants automatically.  The plain Nix build
is not published: its ELF interpreter is a ~/nix/store~ path, so only Nix hosts
can run it, and they build it from the flake or a binary cache instead.

The one exception is a crate that links Apple frameworks — anything that
(transitively) pulls ~cpal~, ~objc2-*~, ~core-foundation~, ~security-framework~,
~coreaudio-sys~, and similar.  This is not CLI-specific; the ~server~ crate can
link them just as readily — and it does whenever the foundation ~auth~ feature
is on, whose TLS stack links the ~Security~, ~SystemConfiguration~, and
~CoreFoundation~ frameworks.  Such a crate needs Apple's framework headers and
link stubs, which come from the (unfree) Apple SDK.

Enabling it is a single opt-in: set ~"apple-frameworks": true~ at the top level
of ~rust-template.json~ (the same flag shape as ~"windows-msvc"~).  That hands
~mkDarwinCrossPackages~ its ~appleSdk~, taken from a quarantined unfree
~nixpkgs~ (~foundation.lib.pkgsUnfreeFor~) that accepts the darwin-gated Apple
SDK licence.  A ~cli~/~server~ spawn ships with the flag already ~true~ because
its server enables ~auth~; a ~cli~/~lib~-only spawn ships it ~false~.

Because ~apple-sdk~ is unfree and darwin-gated, ~pkgsUnfreeFor~ accepts both
~allowUnfree~ and ~allowUnsupportedSystem~ — but only for that /quarantined/
instance, so the licence acceptance never widens the free package graph your
project actually builds against.  ~appleSdk~ is ~apple-sdk.src~, a plain fetch
of the SDK's inert data (headers and ~.tbd~ stubs); the full ~apple-sdk~ package
does not build on Linux, but its ~.src~ does.  Keeping the acceptance tied to a
flag in /your/ ~rust-template.json~ is deliberate — the licence consent is
visible in your project, not hidden in the foundation library.  Left ~false~, a
pure-libSystem executable cross-compiles licence-free: zig bundles the libSystem
stubs, so no Apple SDK is fetched.

** Windows binaries

Windows binaries are built too, for both =x86_64= and =aarch64=, and are also
*cross-compiled on Linux* — but via ~llvm-mingw~ rather than zig, since
~cargo-zigbuild~ does not support Windows targets.  They target the
~*-pc-windows-gnullvm~ triples, so each result is a native Windows PE that runs
on a stock Windows install with *no Cygwin/MSYS2 layer*; the binary depends only
on the operating system's Universal CRT (present on Windows 10 and later).  This
is automatic — ~mkWindowsCrossPackages~ is already wired into ~flake.nix~ and
needs no configuration.  The toolchain (~llvm-mingw~) is a prebuilt fixed-output
fetch, so nothing Microsoft-licensed is downloaded and no Docker image is
involved.

Unlike the macOS cross build, the Windows build needs *no SDK acceptance*.  On
macOS the audio stack pulls the unfree Apple SDK for the CoreAudio framework
stubs (above); on Windows ~cpal~ selects its *WASAPI* backend, which is a
~windows-sys~ FFI binding to a component the operating system already ships —
there is no ~libasound~ or CoreAudio equivalent to satisfy, so the audio stack
cross-compiles with the same ~commonArgs~ the other targets use.

Unlike the darwin cross build (which only runs on ~x86_64-linux~), the Windows
build is *host-agnostic*: ~nix build .#cli-x86_64-windows~ and its
~-aarch64-windows~ sibling work on a contributor's Mac as readily as in CI.  Two
constraints are worth knowing:

1. the toolchain must be *Rust ≥ 1.91* — the floor at which the aarch64 gnullvm
   standard library became available; the pinned ~rust-bin.stable.latest~ in
   ~flake.nix~ satisfies this, so this only matters if you pin an older
   toolchain; and
2. the release verifies the *x86_64* binary by running it under ~wine~ (the
   ~windowsSmoke~ flake check, gated to ~x86_64-linux~), while the *aarch64*
   binary is build-verified only — no arm64-Windows runner exists, and ~wine~
   cannot execute an arm64 PE.

Windows release assets ship as =.zip= (with the =.exe= inside and the redundant
suffix dropped from the archive name), the format Windows users expect, rather
than the =.tar.gz= used for the Unix-like targets.

*** MSVC-ABI Windows binaries (opt-in)

The gnullvm build above covers pure Rust and any dependency whose C compiles
with ~llvm-mingw~ — which includes this project's audio stack.  A dependency
that specifically requires the *MSVC ABI* — a prebuilt MSVC-only library, MSVC
intrinsics — would instead need the ~x86_64-pc-windows-msvc~ target.  This
project has none, so the variant stays off; the escape hatch is documented here
in case a future dependency forces it.

It is opt-in: set ~"windows-msvc": true~ at the top level of
~rust-template.json~.  That single flag builds the ~<crate>-x86_64-windows-msvc~
variant and adds its release-binary row in CI; leaving it absent (the default)
builds no MSVC variant and touches no Microsoft SDK.

MSVC is *x86_64-only*: on ~aarch64-pc-windows-msvc~ the ~cc~ crate drives clang
through its GNU rather than its ~clang-cl~ mode, so any dependency that compiles
C fails to build.  arm64 Windows is fully covered by the always-on gnullvm build
above, so this is a narrow escape hatch, not a second full target set.

Enabling it cross-links with the LLVM MSVC toolchain (~clang-cl~ / ~lld-link~ /
~llvm-lib~) against Microsoft's CRT and Windows SDK, which ~xwin~ fetches as a
fixed-output derivation — so, as with gnullvm, there is no build-time download
and no Docker.  Because that fetch accepts Microsoft's SDK licence
(~--accept-license~), turning the flag on accepts that licence *in your own
project*, the same visible consent ~appleSdk~ carries for the Apple SDK.  In
practice this is not a licensing concern for a normal public binary: the default
dynamic CRT redistributes nothing (the Universal CRT is an operating-system
component on Windows 10 and later).

* Changelog conventions

** Changelog structure

~CHANGELOG.org~'s ~* Upcoming~ section uses these subheadings:

- ~** Added~ — features or behavior added.  This is the loose "what's new"
  section: anything an adopter would describe as "the next release does X now"
  belongs here, even when previous releases also did something different in the
  same surface.
- ~** Fixes~ — bug fixes.
- ~** Breaking~ — backward-incompatible changes.  Required when the ABI check
  proves a public-signature break; recommended whenever behavioral breakage
  shipped that downstream consumers should know about, even when signatures are
  preserved.
- ~** Maintenance~ — dependency bumps, template syncs, and similar upkeep with
  no adopter-visible behavior change.

A single change may appear under more than one subheading when it fits more than
one.  A fix that also adds an option to opt out of the broken behavior belongs
under both ~** Added~ and ~** Fixes~.

** Changelog style

Each entry should be a complete sentence-or-two written for an adopter reading
the release notes, not a reviewer reading the diff.  Name what changed in terms
of the surface the adopter sees, not the implementation.  Lead with the impact
on an adopter and state what they must do about it — call out the required
action explicitly, or say that none is needed.  Keep the mechanism to a clause;
the commit history and diff hold the full detail, so an entry that reads like a
commit body is too long.  When several internal changes add up to one
adopter-visible outcome, prefer a single entry describing that outcome over one
entry per underlying change.

When no action is needed, the change itself gets a one-sentence budget — no
run-ons.

Write each entry as a numbered list item (~1.~, ~2.~, …) under its subheading,
not a dash bullet.

** Changelog requirements

Every pull request must add at least one entry under ~* Upcoming~; CI rejects a
pull request that adds none.  This keeps the changelog written incrementally,
while the context is fresh, rather than reconstructed from the diff at release
time.

** Changelog examples

This is a bad example for ~Fixes~:

#+begin_quote
1. Dependabot bumps merge on their own again.  The auto-merge that shipped last
   release committed the changelog and then re-ran CI, but a token-dispatched
   re-run cannot trigger the follow-up that does the merge (GitHub suppresses
   it), so bumps sat green but unmerged; the flow now commits, re-runs CI, and
   merges within a single run.  No action needed.
#+end_quote

This sits on the long side, and gives us way too much context about the inner
workings of the code.  As a migrator interested in seeing what changed and what
they need to do, they have to sift that information out.  A better form would
be:

#+begin_quote
1. Dependabot bumps merge on their own again.  No action needed.
#+end_quote
